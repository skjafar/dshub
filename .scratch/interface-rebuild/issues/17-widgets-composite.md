# 17 — Widgets: composite family

**What to build:** The five Widget kinds that show more than a single bound value — data table, alarm list, device info, container, and mini-plot — restyled onto the new design language and the shared configuration surface.

The data table displays many entries at once and includes writable cells, so it inherits the write-path contracts in full; this is the surface the existing write-cell regression test was written against, and that behaviour must survive the rebuild intact. The mini-plot uses the same plotting engine as the Plot Pane, which is why this batch waits on that work. The container groups other Widgets, so it must handle nesting and resizing without corrupting the layout of what it holds.

**Blocked by:** 14, 12

- [x] Data table write cells satisfy the write-path contracts, including the mid-edit overwrite case

## Comments

**Data Table and Alarm List's rows are `BoundWidgetConfig` itself, not a row-specific shape.** A row is a label, a binding, a format and thresholds — exactly what a Value Readout already carries — so `DataTableRow`/`AlarmListEntry` are type aliases for it rather than new interfaces. This is what makes the row editor reusable rather than duplicated: `WidgetConfigDialog.tsx`'s `BindingPicker` and `ThresholdEditor` were extracted from the existing single-binding `BoundFields` section and are now called three ways — once for a single-value kind's own dialog section, once per Data Table row, once per Alarm List entry — rather than three independent pickers. Each row collapses to a summary line until "Configure" expands it, so a Widget with several rows doesn't open with every picker and Table already on screen.

**A row's writability is read off the Map, not configured.** `entryWriteBlockReason` — the same function `Dropdown` and `Value Write` already gate their own write path on — decides per row whether its cell shows a write form at all; a read-only entry or an unwritable Space is withheld entirely rather than shown disabled, matching ticket 07's precedent. The write cell itself (`DataTableRowView` in `DataTableWidget.tsx`) is `ValueWriteWidget`'s exact contract at table-cell scale: the typed value lives in component state, a live reading mirrors it only while nothing has been typed, and Enter and the Send button both go through one form's `submit`. This is the surface the legacy `DataTableWriteCell` regression test was written against; `CompositeWidgets.test.tsx` pins the same mid-edit-overwrite case and the Enter/Send parity against the new component instead.

**Alarm List's "active" is `warn` or `error` from `evaluateThresholds`, replacing the legacy widget's own severity/min-max rule shape entirely.** No second alarm-specific evaluator exists to drift from the shared one. Each `AlarmRow` always mounts regardless of `showInactive` and decides its own visibility by returning `null` — the alternative, the parent filtering the array before mounting, would mean a hidden entry stops evaluating its own threshold and can never reappear on its own once it goes inactive-and-hidden. The legacy widget's "active first" sort was dropped: recovering it would mean lifting every row's evaluated state into the parent to sort by, which the row-per-hook-instance shape (unavoidable — `useWidgetReading` cannot be called in a loop over a variable-length array) makes considerably more code for a nicety, disclosed here as a real, minor, deliberate trim rather than an oversight.

**Device Info carries no binding at all — its config is `{ label }` and nothing else.** Every field it shows (board identity, link state, uptime) comes from the connection itself, the same source `Overview.tsx`'s Identity and Link-uptime cards already read from (`formatFirmware` is now exported from there and reused rather than reimplemented), so there is no address to bind and `WidgetConfigDialog`'s `KindSection` returns `null` for this kind — Label is the whole of its section.

**Container is a Dashboard-within-a-Widget, deliberately.** `ContainerWidgetConfig.childWidgets` reuses `StoredWidget` verbatim (moved into `widgetConfig.ts`, which `dashboardStore.ts` now re-exports, so `ContainerWidgetConfig` can reference it without a circular import back to the store), and its own nested grid reuses the exact `GRID_COLS`/`ROW_HEIGHT`/`GRID_MARGIN` constants the outer Dashboard's grid uses — extracted to `shell/widgets/gridLayout.ts` so the two can't drift apart, and for the identical `correctBounds`-safety reason ticket 14 fixed the column count for in the first place, one level down. A child is added, configured and removed from directly within the Container itself rather than through `DashboardPane`'s own single-selection `configuringWidgetId` — `WidgetProps` grew `paneId`, `editing` and `onConfigChange` for exactly this, read only by `container` (to thread edit-mode gating and persist child changes) and `miniPlot` (see below). `container` is excluded from its own add-Widget menu, and `dashboardStore.ts`'s `isValidStoredWidget` takes an `allowContainer` flag (`false` for a Container's own children) so nesting can't recurse even through a hand-edited settings file, not only through the menu.

**`ContainerWidget.tsx` reads the `WIDGETS` registry inside the component (`useMemo`), not at module scope.** `widgetRegistry.ts` imports `ContainerWidget` as `container`'s own `component`, so a module-level read of `WIDGETS` from inside `ContainerWidget.tsx` runs mid-way through `widgetRegistry.ts`'s own initialization, before its `WIDGETS` export exists — a real circular import between the two, worth deferring to render time rather than restructuring the registry to avoid.

**Mini-Plot reuses `PlotChart` and `plotStream` outright — the same engine `PlotPane.tsx` drives, not a re-implementation.** `plotStream`'s `claimSeries`/`retainSeriesFor` key ownership by a dockview Pane's own id, since a Pane is the only thing dockview's own panel list (and hence `retainSeriesFor`'s cleanup pass) knows about; a Widget has no such identity. `paneId` (the third field `WidgetProps` grew) is the enclosing Dashboard Pane's own id, threaded down unchanged through `container` so a Mini-Plot nested inside one still claims under the Pane that actually appears in dockview's panel list. One consequence, disclosed rather than silently accepted: a Mini-Plot's claim is released only when its whole Dashboard Pane closes (via `retainSeriesFor`) or its bound address changes, never when the Mini-Plot Widget itself is removed from the Dashboard — a real, minor gap at Dashboard-scoped rather than Widget-scoped ownership granularity, judged out of scope for the plumbing it would take to thread a precise per-Widget release through `DashboardPane`'s `handleRemoveWidget`.

**Mini-Plot's own chart is not exercised by the automated tests, only its unbound state is.** `PlotPane.test.tsx` mocks the `uplot` package at the module boundary because jsdom has no canvas 2D context for it to draw into; `CompositeWidgets.test.tsx` does not carry that mock, so only the one path that never constructs a chart — no address bound — is pinned there. The bound, streaming state was verified by hand in a real browser, per this project's testing policy for the same reason dockview drag and react-grid-layout's own drag/resize already are.

**`react-grid-layout` nested two levels deep — the Container's own inner grid inside the outer Dashboard grid — is outside the automated test net for the drag/resize/add-via-live-menu path, beyond what ticket 14's own policy already carved out for one level.** jsdom's `mousedown`/`mouseup` simulation of a full pointer sequence through two nested `react-draggable` instances trips that library's own internal "onDragEnd called before onDragStart" invariant, which does not happen in a real browser. `CompositeWidgets.test.tsx`'s Container coverage pre-seeds a bound child directly in the stored config rather than driving the add-then-configure flow live (that flow, through the same `Menu`/`WidgetConfigDialog` components, is already proven at the outer nesting level by `DashboardPane.test.tsx`) and uses a bare `fireEvent.click` — not `userEvent`'s full pointer sequence — for the one interaction it does drive live, removal.
