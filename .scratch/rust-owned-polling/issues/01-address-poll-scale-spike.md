# 01 — Address-keyed poll registry spike

**What to establish:** whether one `tokio::time::interval` task per actively-polled device address, spawned and torn down as subscribers come and go, holds up at the scale this feature actually needs — potentially dozens of concurrently-open widgets, not the handful of named plots `spawn_plot_task` has production precedent for. This gates the rest of the feature. Nothing else is built until this returns a verdict.

**Status:** ready-for-human

Build a debug-only `#[tauri::command]` (mirror `src-tauri/src/spike.rs`'s shape — it reports over stdout rather than the webview console specifically because WebView2 does not forward webview console output to the launching terminal) plus a throwaway harness, gated the same way the original popout spike was.

- [x] Against the Python emulator (`emulator/dshub_emulator.py`), open ~30 concurrent address subscriptions at mixed intervals (mix of register/parameter/sysRegister addresses, intervals spanning the 50ms floor up to several seconds) — **done, `src-tauri/src/poll_spike.rs` + `client/src/spike/PollLoadSpike.tsx`, run by hand on Windows against `cargo tauri dev`. 30 tasks, intervals staggered 200ms–1.17s on the baseline run and 50ms–1.02s on the floor run, addresses spread across the emulator's registers 0–24.**
- [x] Confirm exactly one request is ever in flight on the wire at a time — `response_matches`'s address correlation depends on this; a design that lets two requests race would corrupt values silently rather than error — **holds by construction, not independently instrumented: every spike task pushes onto the same single-consumer `mpsc::Sender` `queue_request` already uses, so this is the existing architecture's guarantee, not something the new per-address-task shape could break. Consistent with zero response-mismatch symptoms across ~6,700 requests sent over four runs.**
- [x] Confirm task count stays bounded and matches subscriber count (no leaked tasks after unsubscribe; no duplicate tasks for an address with multiple subscribers) — **confirmed. `30/30` alive for the full duration of every connected run (baseline ~36s, floor ~21s, post-reconnect ~22s); dropped to `0/30` promptly and correctly when the connection was killed (no stragglers, no leaked handles); `Stop`/`Start` cycles repeatedly produced exactly 30 fresh tasks with no leftover state from the previous run.**
- [ ] Confirm changing the fastest requested interval for an address (adding then removing a fast subscriber) actually reschedules that address's task, not just on the next natural respawn — **not exercised by this spike.** The harness spawns a fixed set of tasks at fixed intervals for the run's duration; it doesn't model a subscriber joining/leaving mid-run. This is real Phase 1 implementation behavior (the `fastest_interval`/respawn-on-change logic `poll.rs` needs), not a scale question — covered by that module's own unit tests per the spec, not this spike.
- [x] Force a disconnect/reconnect mid-run and confirm every still-registered subscription resumes automatically, with no manual re-subscribe from the frontend side — **confirmed, with one caveat the spike's own design accepts.** Killing the emulator correctly and promptly zeroed the task count (`6/30` → `0/30`, frozen request count — each task's `tx.send` failed and exited cleanly, no hangs or panics). Rust's own `reconnect_loop` re-established the connection in the background with no user action (confirmed indirectly: `spike_resume_poll_load` succeeded on the very first click, no retries needed). One click (**Resume**) was needed to respawn the spike's own 30 tasks — expected and by design, since the spike has no `resume_poll_subscriptions` equivalent of its own; that automatic piece is real Phase 1 work, not something a throwaway harness should build. The resumed run's steady-state rate (~61.8–62.9 req/s) was statistically identical to the original baseline (~61.5/s) — full recovery, no leaked tasks, no double-counted requests.
- [x] Confirm the rate limiter and one-request-in-flight serialization hold under this load — no channel backpressure stalls, no requests silently dropped — **confirmed at both intervals tested.** 200ms base: ramped from an initial burst (all 30 tasks fire their un-skipped first tick simultaneously) down to a stable **~61.5 req/s**, with strictly linear cumulative growth thereafter (2217 requests over 36.1s = 61.4/s average, matching the tail instantaneous rate). No independent cross-check was made against the emulator's own printed stats (not captured), but the harness's internal counters were self-consistent throughout every run, with zero unexplained count drops while connected.
- [x] Record whether 50ms (matching `pollRegistry.ts`'s existing floor) is actually sustainable at ~30 concurrent addresses against the emulator, or whether that number needs revisiting before the real implementation ships — **sustainable, cleanly.** 50ms base interval held `30/30` tasks alive for the full ~21s run at a stable **~116–117 req/s** (roughly double the 200ms run's rate, as expected), with the same strictly linear growth and no sign of stalling, missed-tick pileup, or degradation over the run's duration.

If this doesn't hold up at scale, that's a complete and useful result — record what broke and what scale it broke at, and revisit the per-address-task design (candidates: a bounded worker pool instead of one task per address, or a coarser scheduling grain) before writing the rest of the feature against an assumption that doesn't hold.

## Verdict (2026-08-16)

**Pass.** The per-address-task design holds at 30 concurrent addresses, at both the 200ms baseline and the 50ms floor, and recovers cleanly across a real disconnect/reconnect. The one item not exercised (dynamic interval rescheduling) is real `poll.rs` implementation behavior rather than a scale question, and is covered by that module's own planned unit tests instead. Phase 1's full implementation (`src-tauri/src/poll.rs`, the `subscribe_address`/`unsubscribe_address` commands, and the frontend rewiring described in `spec.md`) is unblocked.

`src-tauri/src/poll_spike.rs` and `client/src/spike/PollLoadSpike.tsx` are throwaway and should be deleted once Phase 1 ships, per the same convention `spike.rs`/`PopoutSpike.tsx` followed for issue 01 of the original Daughter Windows work (kept as historical record there rather than deleted immediately — same call applies here: leave them until Phase 1 lands, then remove alongside it).
